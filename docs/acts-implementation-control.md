# Инструкция пользователю: управление внедрением модуля актов

## 1. Назначение

Этот файл нужен для управления работой Codex по модулю актов.

Основной roadmap внедрения: `docs/acts-roadmap.md`.

Этот файл не описывает архитектуру модуля. Он отвечает на практический вопрос: что писать в чат, когда принимать этап, когда останавливать, когда разрешать commit/push.

## 2. Главный принцип

Не просить Codex делать весь модуль сразу.

Работа идет по этапам:

1. Codex выполняет один этап.
2. Codex останавливается.
3. Вы проверяете результат.
4. Если результат принимается, разрешаете следующий этап.
5. Commit/push разрешаются отдельно.

Так снижается риск, что Codex смешает модель, UI, DOCX, импорт и статистику в один большой непроверяемый кусок.

## 3. Старт работы

Когда нужно начать внедрение или продолжить после паузы, пишите:

```text
Работай строго по C:\Users\Olga\AKB5\docs\acts-roadmap.md.
Для управления процессом используй C:\Users\Olga\AKB5\docs\acts-implementation-control.md.

Выполни следующий этап roadmap.

Важно:
- сначала проверь ветку и git status;
- работай только в C:\Users\Olga\AKB5;
- AGENTS.md не трогай и не включай в commit;
- commit/push не делать без отдельной команды;
- после этапа остановись и дай отчет.
```

## 4. Если нужно выполнить только контроль состояния

Используйте это перед началом реальной разработки или после нового чата:

```text
Выполни только Stage 0 / Контроль состояния по C:\Users\Olga\AKB5\docs\acts-roadmap.md.

Код приложения не менять.
Документы не менять.
Commit/push не делать.

Дай отчет:
- активная ветка;
- HEAD;
- sync state;
- незакоммиченные изменения;
- незапушенные изменения;
- можно ли безопасно начинать следующий этап.
```

Важно: фраза `Код приложения не менять` здесь относится только к Stage 0. Начиная со Stage 1 код менять можно, но только в границах конкретного этапа.

## 5. Как принять этап и разрешить следующий

Если результат этапа проверен и устраивает, пишите:

```text
Этап принимается.
Продолжай следующий этап по C:\Users\Olga\AKB5\docs\acts-roadmap.md.

Не расширяй scope этапа.
После выполнения остановись и дай отчет.
Commit/push не делать.
```

## 6. Как отправить на исправление

Если этап не принимается, пишите:

```text

Проблема:
[кратко что не работает]

[как должно быть]

Фактическое поведение:
[что происходит]

Исправь только эту проблему.
Следующий этап не начинай.
Commit/push не делать.
```

## 7. Как остановить работу

Если нужно остановить Codex в любой момент, пишите:

```text
Стоп.
Ничего не коммить и не пушить.
Не переходи к следующему этапу.

Дай статус:
- ветка;
- измененные файлы;
- что успел изменить;
- какие проверки запускались;
- что осталось незавершенным;
- какой безопасный следующий шаг.
```

## 8. Когда разрешать commit

Commit разрешайте только после того, как:

1. этап принят;
2. отчет понятен;
3. нет сомнений по измененным файлам;
4. `AGENTS.md` не должен попасть в commit.

Команда:

```text
Commit принятого этапа.

Перед commit:
- проверь git status;
- покажи staged files;
- убедись, что AGENTS.md не staged;
- в commit включи только изменения принятого этапа.

После commit дай hash и статус.
Push не делать.
```

## 9. Когда разрешать push

Push разрешайте только после успешного commit.

Команда:

```text
Push ветки act.

Перед push:
- проверь активную ветку;
- проверь git status;
- проверь последний commit;
- push только origin act.

После push дай статус синхронизации.
```

## 10. Что писать после ручной проверки

Если ручная проверка прошла:

```text

Этап принимается.
Дай статус и предложи следующий этап.
Commit/push пока не делать.
```

Если ручная проверка не прошла:

```text
Ручная проверка этапа не прошла.

[описание]

[описание]

Фактическое поведение:
[описание]

Следующий этап не начинай.
Commit/push не делать.
```

## 11. Когда просить сборку exe

Сборку exe просите только когда этап затрагивал приложение и нужно проверить руками.

Команда:

```text
Подготовь сборку для ручной проверки текущего этапа.

Важно:
- сначала выполни нужные короткие тесты;
- собери Release;
- путь к asutpKB.exe дай первым;
- GUI не запускай без моего отдельного разрешения;
- commit/push не делать.
```

## 12. Новый чат

Если контекст вырос или нужно перейти в новый чат:

```text
Новый чат.
Подготовь handoff по AKB5 act.

Обязательно:
- укажи repo;
- branch;
- HEAD;
- sync state;
- незакоммиченные изменения;
- незапушенные изменения;
- последний принятый этап;
- validation status;
- следующий точный шаг;
- дай готовый промт для нового чата.
```

Используйте короткие фразы:

```text

```

```text
Этап не принимается. Исправь только указанную проблему.
```

```text

```

```text
Commit принятого этапа.
```

```text

```

## 14. Что не писать

Не пишите:

```text
Делай все этапы сразу.
```

```text
Продолжай как считаешь нужным.
```

```text
Сделай модуль актов полностью.
```

Такие формулировки повышают риск, что Codex смешает этапы и сделает большой непроверяемый diff.

## 15. Минимальная приемка каждого этапа

Перед фразой `Этап принимается` проверьте:

1. отчет содержит список измененных файлов;
2. понятно, какие тесты запускались;
3. понятно, что не проверено;
4. Codex остановился, а не начал следующий этап;
5. нет изменений вне scope этапа;
6. `AGENTS.md` не попал в staged/commit;
7. если была сборка, путь к exe указан первым.

## 16. Быстрый рабочий цикл

Обычный цикл выглядит так:

1. Написать стартовую команду из раздела 3.
2. Дождаться отчета.
3. Проверить результат.
4. Если все нормально, написать: `Этап принимается. Продолжай следующий.`
5. Если этап крупный или важный, сначала провести ручную проверку.
6. После принятого набора изменений отдельно разрешить commit.
7. После commit отдельно разрешить push.
