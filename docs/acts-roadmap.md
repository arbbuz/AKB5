# Roadmap модуля актов

## 1. Назначение

Этот документ фиксирует рабочий план внедрения модуля актов в `asutpKB`.

План создан для ветки `act` и должен использоваться как основной ориентир перед реализацией. Код приложения по этому документу не меняется автоматически: каждый этап внедряется только после отдельного разрешения пользователя.

## 2. Зафиксированные решения

1. Модуль актов реализуется как собственная функциональность `asutpKB`, без встраивания и запуска `ActsManager.exe`.
2. Упаковка ActsManager, Costura, Fody и single-file подход из донора не переносятся.
3. Правила вкладок не меняются.
4. Точка входа в MVP: `Lvl3 -> Состав -> Rack -> ПКМ по строке оборудования -> Сформировать акт`.
5. Исходная формулировка roadmap про вкладку `Карточка` для Lvl3 не применяется: в текущей архитектуре работаем именно со вкладкой `Состав`.
6. Контекстное меню не генерирует документ напрямую. Оно открывает форму проверки и редактирования акта.
7. Для пользователя может быть одна команда `Сформировать документ`, но внутри приложение сначала сохраняет акт в базе, потом генерирует DOCX. Это нужно, чтобы при ошибке шаблона, пути или генерации не потерять данные формы.
8. Автозаполнение осторожное: подтягивать только данные, которые однозначно есть в выбранной строке Rack и текущем Lvl3.
9. `OrderNumber` не считать серийным номером.
10. Серийный номер заполнять автоматически только если появится реальный источник данных; иначе поле остается пустым или ручным.
11. Сформированные документы хранить в настраиваемой папке. Значение по умолчанию: `Documents\Acts`.
12. В базе по возможности хранить относительный путь к документу.
13. Существующий DOCX не затирать молча.
14. Шаблоны DOCX должны быть внешними файлами, а не зашитыми в C#.
15. Генерацию DOCX желательно держать в отдельной сборке/плагине, чтобы не увеличивать основной exe без необходимости.
16. `docs/plans.md` обновляется только после проверки и принятия этого roadmap пользователем.

## 3. Границы MVP и последующих этапов

### 3.1. MVP

MVP должен доказать основной пользовательский сценарий без лишнего расширения области:

1. Модель акта и хранение в `.akb`.
2. Связь акта с Lvl3 и выбранной строкой оборудования Rack.
3. Создание акта через ПКМ на вкладке `Состав`.
4. Форма акта с минимальным автозаполнением и ручным редактированием.
5. Сохранение записи акта в базе.
6. Генерация DOCX из внешнего шаблона.
7. Сохранение документа в `Documents\Acts` или другой настроенной папке.
8. Имя файла вида `2026-0001_Акт_выхода_из_строя_Модуль_DI.docx`.
9. Запись акта в журнале.
10. Фильтры журнала актов по колонкам.

### 3.2. Этап после MVP

После подтверждения MVP:

1. Второй тип акта.
2. Справочники исполнителей.
3. Справочники подписантов.
4. Настройки шаблонов.
5. Настройки нумерации.
6. Статусы и ограничения редактирования.
7. Защита от перезаписи документов.
8. База актов по годам.
9. Импорт из ActsManager.

### 3.3. Этап после стабилизации

После стабилизации основного модуля:

1. Статистика по актам.
2. Экспорт статистики в `.xlsx`.
3. Сводные отчеты `.docx`.
4. Отчеты по Lvl3.
5. Отчеты по моделям оборудования.
6. Отчеты по критериям отказов.
7. Расширенные фильтры и поиск по актам.
8. Версии шаблонов.
9. Версии документов.

## 5. Модель данных

### 5.1. Типы

Минимальные сущности:

1. `KbAct`.
2. `KbActExecutor`.
3. `KbActDocument`.
4. `KbActNumberSequence`.
5. `KbActEquipmentSnapshot`.

Архитектурный задел, который может быть введен после MVP или как легкая модель без экранов:

1. `KbActTemplate`.
2. `KbActSettings`.

### 5.2. Тип акта

Одна сущность акта с полем `ActType`.

Минимальные значения:

1. `InspectionWork` - акт осмотра / выполненных работ.
2. `EquipmentFailure` - акт выхода из строя оборудования.

Для MVP допустимо реализовать только один тип, если это будет отдельно подтверждено перед кодом. Модель не должна закрывать путь ко второму типу.

### 5.3. Статус акта

Добавить `ActStatus`.

Минимальные значения:

1. `Draft` - черновик.
2. `Generated` - документ сформирован.
3. `Signed` - подписан.
4. `Cancelled` - аннулирован.
5. `Archived` - архив.

Для MVP можно использовать только `Draft` и `Generated`, но модель и БД должны позволять добавить остальные статусы без ломки.

Правило: подписанный или сформированный акт нельзя молча перегенерировать с перезаписью существующего файла.

### 5.4. Поля `KbAct`

Обязательные или базовые поля:

1. `ActId`.
2. `ActYear`.
3. `ActNumber`.
4. `ActType`.
5. `Status`.
6. `ActDate`.
7. `Lvl3NodeId`.
8. `Lvl3NameSnapshot`.
9. `ObjectPathSnapshot`.
10. `RackId`.
11. `RackNumberSnapshot`.
12. `CompositionEntryId`.
13. `EquipmentSnapshotJson` или отдельная структура snapshot.
14. `CreatedAt`.
15. `UpdatedAt`.

Поля из roadmap/donor, которые нужны для сохранения смысла актов и будущего импорта:

1. `FailureDate`.
2. `FaultDescription`.
3. `FailureReason`.
4. `InspectionResult`.
5. `FaultCriterion`.
6. `RequestDocument`.
7. `ActualLaborHours`.
8. `CustomerName`.
9. `CustomerPosition`.
10. `CreatedBy`.

Эти поля не обязаны все отображаться в MVP-форме. В БД и модели их лучше предусмотреть сразу как nullable/пустые, чтобы не потерять данные при импорте ActsManager и не делать лишнюю миграцию сразу после MVP.

### 5.5. Snapshot оборудования

Акт должен хранить не только ссылки, но и снимок оборудования на момент создания.

Причина: оборудование в `asutpKB` может быть переименовано, заменено или удалено позже, а старый акт должен сохранить исторически корректный текст.

Минимальный snapshot:

1. `Lvl3Name`.
2. `ObjectPath`.
3. `RackId`.
4. `RackNumber`.
5. `RackName`.
6. `CompositionEntryId`.
7. `ComponentType`.
8. `Model`.
9. `OrderNumber`.
10. `SerialNumber`.
11. `Notes`.

`SerialNumber` заполняется только из реального поля или вручную. `OrderNumber` не подменяет `SerialNumber`.

## 6. Автозаполнение формы

### 6.1. Разрешено автозаполнять

1. Lvl3 / объект.
2. Путь объекта.
3. Rack / шкаф, если он есть в модели.
4. Тип оборудования.
5. Модель / имя оборудования.
6. Заказной номер.
7. Дату акта.
8. Тип акта по умолчанию.
9. Предлагаемый путь сохранения документа.
10. Предлагаемое имя файла.

Slot не выводить в акт и не использовать как пользовательское поле. Внутренняя связь с выбранной строкой состава хранится через `CompositionEntryId`.

### 6.2. Значения по умолчанию и ручная корректировка

Поля формы должны заполняться по умолчанию по логике ActsManager там, где значение можно определить без риска исказить данные. Пользователь должен иметь возможность изменить эти значения перед формированием документа.

Можно задавать значения по умолчанию:

1. Тип акта.
2. Дату акта.
3. Дату отказа, если она вводится в форме и есть понятное default-значение.
4. Критерий отказа.
5. Заявку/документ-основание.
6. Трудозатраты.
7. Исполнителей.
8. Подписантов.
9. Должности.
10. Типовые тексты причины отказа и результата осмотра.

Правила:

1. Все такие значения должны быть редактируемыми.
2. Значения по умолчанию не должны быть зашиты в код навсегда; для MVP допустим минимальный набор, дальше вынести в справочники/настройки.
3. Не автозаполнять только то, для чего в `asutpKB` нет достоверного источника.
4. `OrderNumber` не подставлять как `SerialNumber`.

## 7. Путь документов

Это правило относится только к месту сохранения DOCX.

1. Значение по умолчанию: `Documents\Acts`.
2. Путь должен быть настройкой модуля актов.
3. Если возможно, в базе хранить относительный путь.
4. Если относительный путь невозможен, хранить полный путь.
5. При переносе базы относительный путь должен оставаться рабочим, если папка документов перенесена вместе с базой/приложением.
6. На первом этапе не раскладывать документы по папкам Lvl3.
7. Существующий файл не перезаписывать молча.

Открытый технический выбор перед реализацией: относительно чего строить путь по умолчанию - папки базы или папки приложения. Предпочтение: рядом с базой/приложением через настройку, с относительным хранением где возможно.

## 8. Нумерация и имя файла

### 8.1. Нумерация

Формат номера:

```text
2026-0001
2026-0002
2026-0003
```

Правила:

1. Год берется из даты акта.
2. Номер идет по счетчику внутри года.
3. Номер дополняется нулями до 4 знаков.
4. Номер уникален внутри базы.
5. При импорте из ActsManager старый номер сохраняется.
6. Ручная правка номера - не в MVP, только после отдельного решения.

### 8.2. Имя файла

Шаблон:

```text
{Год}-{Номер}_{ТипАкта}_{КраткоеИмяОборудования}.docx
```

Пример:

```text
2026-0001_Акт_выхода_из_строя_Модуль_DI.docx
```

Правила:

1. Имя очищается от запрещенных Windows-символов.
2. Слишком длинное имя сокращается предсказуемо.
3. Коллизия имени не должна приводить к молчаливой перезаписи.
4. После успешной генерации путь документа сохраняется в акте/документе.

### 9.1. Шаблоны

Внешние шаблоны:

```text
Templates\Acts\inspection_act.docx
Templates\Acts\equipment_failure_act.docx
```

Минимальные placeholders:

```text
{{ActNumber}}
{{ActDate}}
{{Lvl3Name}}
{{RackName}}
{{EquipmentName}}
{{EquipmentType}}
{{EquipmentModel}}
{{EquipmentSerial}}
{{FaultDescription}}
{{FailureReason}}
{{InspectionResult}}
{{ExecutorsTable}}
```

Дополнительные placeholders для полей donor/roadmap:

```text
{{FailureDate}}
{{FaultCriterion}}
{{RequestDocument}}
{{ActualLaborHours}}
{{CustomerName}}
{{CustomerPosition}}
```

### 9.2. Генератор

Предпочтительная архитектура:

1. Контракт генерации в основном проекте/общем слое.
2. Реализация генерации DOCX в отдельной сборке/плагине.
3. Использовать текущий подход загрузки плагинов по аналогии с Excel/PDF, если это не усложнит MVP чрезмерно.
4. Не добавлять вес OpenXML в основной exe без необходимости.

Правила:

1. Отсутствие шаблона дает понятную ошибку.
2. Неизвестный placeholder не должен приводить к падению приложения.
3. Ошибка генерации не должна терять данные формы.
4. Акт сохраняется в базе перед генерацией документа.
5. Сформированный документ связывается с актом.

## 10. Сохранение, snapshot и change log

Это правило относится к жизненному циклу данных, а не к undo/redo.

### 10.1. Обязательно

1. Акты участвуют в обычном save/load `.akb`.
2. Акты попадают в `SavedData`.
3. Акты попадают в снимки базы.
4. Восстановление из снимка восстанавливает акты.
5. JSON-совместимость не должна ломаться, если экспорт/импорт JSON продолжает использовать `SavedData`.

### 10.2. Change log

Логировать крупные события:

1. Создан акт.
2. Изменен акт.
3. Сформирован документ.
4. Аннулирован акт.
5. Импортированы акты.

Не нужно логировать каждое изменение каждого поля.

### 10.3. Не включать в MVP

1. Полноценный undo/redo актов.
2. Детальный audit trail по каждому полю.
3. Сложную систему прав.

## 11. Контроль внедрения

Эти правила применяются перед каждым этапом реализации, чтобы не смешивать направления и не ломать существующую вкладку `Состав`.

1. Перед изменениями проверять `git status --short --branch`.
2. Работать в ветке `act`.
3. Не включать локальный `AGENTS.md` в коммиты без отдельного разрешения.
4. Не менять правила вкладок Lvl3.
5. Не менять поведение Rack-таблиц шире необходимого для команды `Сформировать акт`.
6. Каждый этап должен иметь проверяемый результат.
7. Storage/model changes выполнять и проверять до UI, если этап зависит от хранения.
8. UI должен вызывать сервисы, а не содержать логику DOCX/SQLite напрямую.
9. После этапа фиксировать, какие тесты и ручные проверки выполнены.
